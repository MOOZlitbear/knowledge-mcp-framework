# 自动整理设计

目标：把收件箱里积压的提交，按主题落进项目卡并登记，尽量不用人盯着。

这里记录的是一种**克制的自动化**：模型只负责“归类与摘要”，写卡动作由脚本按固定规则执行，所有修改可回滚。

## 1. 触发

- systemd timer，每天固定时间（示例 22:00，带 1–3 分钟随机延迟）。
- `Type=oneshot`：跑完即退，不常驻。
- `Persistent=true`：主机重启错过触发时补跑一次。

## 2. 状态

| 状态 | 位置 | 用途 |
|---|---|---|
| 处理登记 | `inbox/registry.md` | 已归并条目的路径 + revision + 落点 |
| applied | `state/applied.json` | 已落卡条目，防登记失败导致重复追加 |
| 提案 | `90-automation/proposals/YYYY-MM-DD.md` | 本次归类结果，供审计 |
| 应用日志 | `90-automation/apply-logs/YYYY-MM-DD.md` | 每条落到哪张卡、状态与错误 |

未处理 = 收件箱清单 − 处理登记 − applied。

## 3. 流程

```text
scan → read items → PII filter → LLM plan → validate
     → write proposal → append cards → update registry → write log
```

1. **扫描**：分页列出收件箱，排除登记文件本身。
2. **读取**：取标题、项目、时间、revision 与 900 字摘要。
3. **PII 过滤**：命中手机号/身份证/病历号模式的条目不送模型，列入「需人工」。
4. **模型**：要求输出 JSON，每个条目必须且只能属于一个分组或 unassigned。
5. **校验**：
   - 目标必须是 `projects/` 下的 `.md`，拒绝 `..`；
   - 每条路径必须真实存在于本次输入；
   - 每个分组必须有 markdown 块，长度有上限；
   - 生成内容再过一遍 PII 检查。
6. **落卡**：
   - 已有卡：读取 revision → 追加 `## 自动整理 <时间>` 小节 → CAS 更新；
   - 新卡：仅当目标不存在时创建；
   - 每成功一组就把该组条目写入 applied。
7. **登记**：追加「路径 | revision | 落点」表格；冲突时重读一次再写。
8. **日志**：成功/失败都写，失败以非零退出。

## 4. 为什么“只追加”

- 模型重写整张卡容易丢历史、改口旧结论；
- 追加块是纯增量，冲突面小，回滚只需删掉该小节；
- 代价是卡会变长，需要定期人工梳理。

## 5. 幂等

- applied 在每组落卡成功后立即 fsync 落盘；
- 即使登记写入失败，下一次也不会重复追加；
- 重复运行同一天会生成带时间的第二个小节，可通过日志识别。

## 6. 成本控制

- 每批最多 N 条（示例 25），单块上限 5000 字；
- 只送摘要，不送全文；
- 没有未处理条目时不调用模型。

## 7. 失败处理

- 模型返回非法 JSON / 校验失败：写失败日志，不落卡；
- 落卡中途失败：已成功的组已记录，错误日志标明失败组；
- MCP 不可用：整轮失败，退出码非零，systemd 记录 failed。

## 8. 停用与降级

- 完全停用：`systemctl disable --now <timer>`；
- 只提案不落卡：给脚本加 `--no-apply`；
- 只试跑：`--dry-run`。
